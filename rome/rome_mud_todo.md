## 📋 Bounty board is built - ✅ this session, first of two requested systems (bounties, then quests)

- [x] **Design discussed and confirmed before any code was written**, per direct request: kill-only for v1 (no fetch/item objectives - no clean item pool exists yet), a personal/parallel board (no shared contention, no claim/expiry logic needed) explicitly chosen with the follow-up requirement that party kills be handled correctly, a real physical board object rather than a from-anywhere command, and gold/XP/item rewards only (no new earned-titles system bolted on).
- [x] **`world/bounties.py`**: `BOUNTY_TIERS` (novice/veteran/champion, tiered by player level) draws exclusively from the Cloaca Maxima's existing `sewer_npc` roster - deliberately not the Colosseum/Ludus (consensual training content, not "wanted criminal" fare) or the Deeper Sands. `roll_bounty()` picks a random target + count from the caller's own tier; reward XP is `count × target's own xp_reward × 0.75`, gold derived the same way every other gold reward in the game already is (`GOLD_PER_XP_DIVISOR`) - no hand-invented second economy.
- [x] **A real board** (`BountyBoard`, placed at the Forum's real "The Rostra" room - the actual historical spot Romans posted public notices) via `world/setup_bounties_live.py`. `bounty` / `bounty accept` / `bounty turnin` / `bounty abandon` (`CmdBounty`) - completing the kill count doesn't auto-pay, you have to physically return and turn in, giving the board recurring relevance rather than a silent background counter.
- [x] **Party-aware by design, not as an afterthought** - raised directly as a concern before building started. Progress is credited to every character in the defeated NPC's `damage_log` (the exact same population that already splits ordinary combat XP/gold fairly on a group kill) who individually has a matching active bounty - not just whoever landed the killing blow, and not one shared bounty per party. Two party members can be working two completely different bounties off the same shared fight with zero special-casing. This composes for free with the same session's new party XP bonus (see below) - a party bounty-hunting together gets both rewards from the same kill, no interaction code needed between the two systems.
- [x] **A real, load-bearing bug caught by a test before this ever went live.** The original design matched a defeated NPC against its Evennia spawn-prototype tag (`PROTOTYPE_TAG_CATEGORY`), mirroring the documented convention already used in `world/economy.py`. A dedicated test spawning a real NPC and checking that tag failed - it turns out that mechanism only fires when `spawn()` is given a *string* key looked up through Evennia's prototype registry, not when given the raw dict object directly, which is exactly how every sewer NPC setup script actually spawns them. Fixed by matching on the NPC's own stable display `key` instead (e.g. "a Subura footpad") - already a literal field on every prototype dict, and nothing in the game ever renames a hostile NPC. Exactly the reason this project writes a load-bearing test against the real mechanism before trusting an assumption, not after.
- [x] New `help bounty` topic; `help groupcombat` cross-references it.
- [ ] **Next up**: the quest framework (generic `db.quest_log`, a `quest` command with an implicit-room-NPC target matching `CmdChallenge`'s own established convention, `"kill"`/`"talk"` step types only for v1) and the two starter quests already agreed - the Aventine's secession elder (a "talk" quest built entirely from existing content) and the Saepta Julia's election officials (a "kill" quest against a new named troublemaker NPC).

## 🚶 Movement now costs SP - ✅ this session, real bugs found and fixed along the way

Direct request following the geographic-accuracy audit: the user wants long-distance travel to be able to genuinely require a rest stop, not just be a free, instant scroll through however many rooms sit between two landmarks.

- [x] **Design discussion first, per request**: I recommended scoping the cost to only "road/journey" zone-tagged rooms (to avoid taxing routine exploration inside the game's largest zones - the 99-room Forum, the 85-room sewers). The user chose the broader option instead: SP cost applies to every ordinary move, everywhere, at 1 SP/room (`MOVEMENT_SP_COST`, `world/combat.py`) - a real, explicit override of my own recommendation, not an oversight.
- [x] **Mechanic**: `CombatCharacter.at_pre_move` blocks the move outright ("You're too exhausted to go on - rest here first.") if current SP is below the cost, rather than letting it go negative - resting (`rest`, already-existing regen system) is the only way to recover and continue. A one-time warning fires the first time a move leaves SP at/below 25% of max, clearing again once SP recovers above that line. Exempt: gods (`db.level > 100`), dead characters, and anything that isn't a real typed exit move (NPC wandering, system teleports) or has no account behind it (NPC safety net).
- [x] **Death-state follow-up, same request**: a real death (level 6+) now explicitly zeroes HP, MP, *and* SP (previously only HP was reliably at/near 0 from the killing blow) - this is what makes a dead character unable to cast a spell or use a skill true by construction, not just by the separate `is_dead` checks those commands already had. `rest` now refuses to work at all while dead, so resources genuinely stay at 0 until an actual resurrection - which still fully restores everything, as it already did.
- [x] **Two real bugs caught by the test suite before this ever went live**: `test_low_level_defeat_restores_stats_and_sends_to_cells` and `test_resurrect_fully_heals_and_returns_to_cells` both started failing (29 SP instead of 30) the moment the movement cost was added - because the safe-respawn and resurrection code paths relocate a player via plain `move_to()`, which defaults to `move_type="move"`, the exact thing the new cost hooks into. A full audit of every place in the codebase that programmatically moves a player character found **four more** of the same latent gap that hadn't been caught by an existing test yet: the "gate" teleport spell, the Underworld ferry's auto-carry, and two Colosseum questline sequences (the maintenance-tunnel sneak, the hidden-stairwell escape) plus the "world shifts" arena teleport. All six fixed by explicitly passing `move_type="teleport"` at the call site - the same convention already used for `@tel` and the divine-presence system, just never applied consistently before now. Full test suite re-run clean afterward.
- [x] **New `help sp` topic** (`world/help_setup.py`) - SP previously had no dedicated help entry of its own, only mentions inside `statup` and the per-skill cost display. Explains both what SP is for (skills) and the new movement cost, plus the god/dead exemptions.

## ⏱️ Real cooldowns for skills/spells; resurrect gated on crossing the river — ✅ this session

- [x] **Cooldowns finally built.** The gap flagged during the original combat feedback pass ("zero cooldowns exist anywhere in world/combat.py") now has a real, generic mechanism: `cooldown_for_level()` derives a default cooldown (0/2/3/4/5 turns) from an ability's `level_required`, applied automatically by `CmdCast`/`CmdUseSkill` via `spelldata.setdefault("cooldown", ...)` - no per-ability data entry required, though any entry can still override it explicitly. A "turn" ticks down at that character's own `at_turn_start` in combat, or their own `at_update` tick out of combat - the same two hooks conditions already use, so cooldowns behave consistently whether or not a fight is happening. Low-tier (level <20) spells/skills stay uncooled - cost was already enough of a gate for those; this specifically targets the "just spam your best move every turn" problem once something's affordable.
- [x] **Deliberately scoped to the player-facing commands only** - NPC AI calls spellfuncs/skillfuncs directly and bypasses `CmdCast`/`CmdUseSkill` entirely, so NPCs are unaffected. The original complaint was about a player's own turn-to-turn decision loop, not NPC behavior, so this wasn't extended to NPCs.
- [x] **Blessing of Asclepius (resurrect) can no longer reach a target before they've crossed the river.** Real gap found: this spell does a *global* search for a dead target specifically because they're nowhere near the caster - which meant a Medicus could revive someone the instant they died, before the mandatory ~15-minute wait for Charon (`CharonTimer`/`db.charon_arrived`) ever had a chance to matter. Now checks `target.db.charon_arrived` before reviving; MP still only spent if the resurrection actually happens, matching the spell's existing "nothing happened, nothing spent" behavior for an already-alive target.
- [x] 12 new tests (`tests_underworld.py` +3, `tests_combat_commands.py` +9) covering the resurrect gate, the cooldown formula tiers, cooldown enforcement/tickdown for both spells and skills, and the equipment-display fix below. Full suite run pending confirmation as of this writing - will follow up if it turns up anything.
- [x] **First-pass tuning, not final balance** - the 0/2/3/4/5-turn tiers by level bracket are a reasonable starting point, not something actually playtested against real fight lengths. Worth revisiting once there's been a real fight or two with a level-20+ ability in the mix.

## 🛡️ Level-scaled weapon/armor formula, new equipment slots — ✅ this session

- [x] **Weapons now derive damage/accuracy from a category+level formula** (`compute_weapon_stats`, `world/combat.py`) instead of a fully static per-prototype `damage_range`. A category (`light_blade`/`ranged`/`polearm`/`heavy_blade`/`staff`/`heavy_weapon` - the exact tags already on every weapon prototype) sets the overall shape; each individual weapon type (`WEAPON_SUBTYPES`, keyed by the existing `weapon_type_name` field) layers a small accuracy/damage delta on top, derived directly from this project's own real, already-live weapon stats rather than guessed - e.g. Dagger and Gladius are both `light_blade` but stay genuinely distinct (Dagger more accurate, Gladius harder-hitting) at every level, not identical the way a pure category-only system would make them. - [x] **Fixed a real growth-rate mismatch found while designing the weapon formula.** The original armor-scaling idea (flat `round(1 + level*0.15) + offset`) grew far slower than weapon damage - mitigation against a comparable hit dropped from ~19% at level 1 to ~4.5% at level 100, i.e. armor becoming nearly irrelevant exactly when it should matter most. `compute_armor_stats` now derives `damage_reduction` from the *same* linear term the weapon formula uses (`14 + 2.1*level`), scaled by a fixed mitigation-percentage target (`ARMOR_MITIGATION_TARGET = 0.18`) - since both formulas share that term, the ratio between them is constant at every level by construction, not just tuned to look close at a couple of checked points. Calibrated against Leather/Scale/Plate's real, already-live `damage_reduction` values (2/4/6) at ~level 4, matching the level the weapon formula's own per-weapon deltas independently landed on. `world/tests_equipment.py` has an explicit regression test asserting this ratio stays flat across levels 1-100 - the actual bug this system exists to prevent from coming back.

Should a two-handed weapon block equipping a shield? (Yes, both directions.) Should equipment be allowed to modify the four core stats (Virtus/Agilitas/Ingenium/Vigor), which CLAUDE.md documents as static-after-chargen everywhere else in the codebase - or only HP/MP/SP? - [x] **Seven equipment slots total**: body (unchanged - still `db.worn_armor`, still the only slot `get_damage` reads `damage_reduction` from), shield (new - `db.worn_shield`, contributes `defense_modifier` only, mutually exclusive with two-handed weapons in both directions via `CmdWield`/`CmdDon`), head/arms/hands/legs/feet (new - `db.worn_head`/`worn_arms`/`worn_hands`/`worn_legs`/`worn_feet`, each only able to modify stats or resource pools via `stat_bonuses`/`resource_bonuses` dicts, applied on don and reversed on doff/drop/give via `apply_equipment_bonuses`/`remove_equipment_bonuses`, never read by `get_attack`/`get_defense`/`get_damage` at all). `CmdDon`/`CmdDoff` are now slot-aware (an item's own `db.armor_slot` field routes it automatically; `doff` now takes an item name since there's more than one thing to remove). `CmdInventory` (the one built earlier this session) shows every equipped slot in its own labeled line. 8 new prototypes in `world/prototypes.py` as proof-of-concept content (3 shields - Parma/Clipeus/Scutum; 5 accessory pieces - Galea/Manica/Fascia Manus/Ocrea/Caligae, real Roman gear names matching the project's existing Latin-flavored naming) - not a full 8-class outfitting pass, that's separate follow-on content work if wanted.

## ⚖️ The Roman Legal System (crime, outlawry, bounties) - large proposal, scoped but NOT started, real open risks

A full player-authored design proposal (homo sacer/aquae et ignis interdictio/Vigiles/Urban Cohorts/Praetor/delatores, a detection-chance formula reusing Agilitas, severity tiers, a wanted-notice board, PvP bounty hunting) - genuinely well-grounded historically and structurally sound. **What's good, unprompted**: the historical grounding is the strongest part of this whole idea - homo sacer specifically is a far better hook than an invented "wanted level," and it's consistent with how every strong mechanic in this game so far (Bacchanalia, cura annonae, the whole PvP-justification policy) has been elevated by real Roman specificity rather than genre-generic naming. **The load-bearing complication, verified directly against the code, not assumed**: making civilian NPCs killable is a much bigger lift than "add a tag." Every flavor NPC in the game (Milo, the Colosseum Herald, all ~50+ NPCs added across the Forum/Subura/Trajan's Market/Baths/Palatine/housing builds) is a plain `evennia.objects.objects.DefaultCharacter` with no `db.max_hp` set - and `attributes.has("max_hp")` is the actual gate every single targeting path in the combat system (`attack`, `cast`, `skill`) checks to decide what's even a valid target. None of these NPCs are currently visible to combat at all, structurally, not by convention. On top of that, `at_defeat()` (`world/combat.py`) has exactly three defeat branches today - `db.respawns` (persistent NPC), `db.instance_owner` (personal instance, deleted outright), or `.account` (a real player) - a civilian NPC with combat stats bolted on would fall through **all three** and just sit at 0 HP doing nothing, because a fourth branch (a real "civilian defeat" path deciding permanence vs. respawn, and firing the crime-detection hook) doesn't exist yet.
- [ ] **Good news found in the same pass**: `db.invincible` already exists and is already checked first in `apply_damage` (`world/combat.py`, "story-critical NPCs that should never be defeated in combat") - the "exclude certain quest NPCs" half of the ask is already a solved, proven mechanism. No new code needed for that part specifically.
- [ ] **A third exclusion category worth adding to the two already named (afterlife, quest NPCs)**: named/unique economy NPCs. Trajan's Market's spice trader and silk merchant, the Ludus weaponsmith, the Forum's four flavor-goods vendors, the Subura's tavern keeper - these are load-bearing for the economy, not scenery. Permanently losing one to a griefer (or even an intended "crime") would break a whole zone's point until/unless it respawns. Recommend either `db.invincible` on named merchants specifically, or a mandatory respawn timer with no permanent-deletion path for anything unique-named - never leave this to "probably fine."
- [ ] **Scope check**: "make all NPCs targetable" as literally stated means retrofitting ~50+ existing NPCs across every zone built this session, each needing real combat stats (hp/accuracy/defense chosen to feel appropriately fragile without being instant-kill or unkillable), a "civilian" tag, zero XP/gold reward (unlike a real `HostileNPC` - a civilian kill must not be a farmable grind), and the new defeat-path above. This is bigger than any single system built this session including the cooldown work - a real multi-session undertaking on its own, not a quick tag-and-go addition. Strongly recommend piloting on a small, deliberately chosen handful of civilian NPCs first (not all 50+ at once) before wiring the rest.
- [ ] **Ambiguity worth resolving before building**: this proposal's trigger is specifically "kill a civilian NPC." The notoriety idea it grew out of (see the feature-ideas list above) was originally about *unjustified player killing*. Worth deciding explicitly whether this system covers both or just civilian NPCs for now - PvP notoriety is arguably simpler to build standalone (every PvP kill is already witnessed by definition, no detection roll needed) and could ship well before the much harder civilian-NPC-combat retrofit is ready, rather than waiting on it.
- [ ] **Real balance risk not yet addressed in the proposal**: NPC guards attacking on sight needs its own calibration pass so detection isn't effectively a death sentence for a lower-level character - a wrongly- or accidentally-flagged player should have a real chance to flee or fight, not just lose automatically. Needs actual playtesting once built, not just a formula on paper (matching this project's own established "don't trust code review alone" rule).
- [ ] **Suggested build order accepted as proposed, with one change**: start step 1 (civilian tagging + detection formula + `db.wanted`/`db.bounty_amount`) on a small pilot set of NPCs, not the full roster, specifically because of the scope-check point above. Steps 2-5 (Praetor/payment, Forum-only guards, holding cell, wanted board) as proposed. Player bounty hunting (step 6) deliberately last, exactly as proposed - this session's independent read agrees it's the highest-risk piece and shouldn't be built until the NPC-only version has actually been played.
- [ ] **Explicitly put on the back burner per direct request**, after hearing the scope/risk pass above - not rejected, just deliberately deprioritized rather than picked up next. Not started. Real design questions above need answers before step 1 begins, whenever it is picked up.

## 📊 Core stats/traits system — ✅ built, one item still open

_(Unchanged - website copy update still open.)_

- [x] **New, direct request: post-chargen stat growth.** Stats are no longer static after chargen - every 3rd level grants one unspent stat point (`world/leveling.py`, `statup` command). Real design process: the first version of the idea (any stat, one uniform cap, resource-pool-dump only after capping) was checked against the actual `get_attack()` formula before implementing, which found `ACCURACY_STAT_MULTIPLIER = 7` makes Agilitas uniquely fragile - even 1-2 points above the old 16 ceiling starts making hits land regardless of the roll, since a weak defender's `defense_value` sits around 50 and the old ceiling already produces a +42 bonus calibrated for ~90%, not 100%. Landed on: Agilitas caps at 18 for every race (hard math constraint, not negotiable per-race), Virtus/Ingenium/Vigor cap at 20 normally or 22 if it's already that race's established chargen specialty (derived from `RACES`' own `stat_mods`, not a separately hand-maintained table). Per further direct request, HP/MP/SP conversion is a real parallel choice available from the very first point (`statup hp|mp|sp`), not only offered once a stat happens to be capped - simpler to implement too, since it removes the conditional logic entirely. 14 new tests, full suite green. `CmdCoreStats` (`stats`) now shows unspent points; `help statup` and an updated `help corestats` cover it in-game.
