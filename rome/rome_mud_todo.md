## ⚖️ PvP: reward, rules, and enforcement decided — ✅ this session, follow-up to the entry below

The open questions the previous PvP entry flagged (consent model, reward, framing) now have real answers, given directly rather than left as further open questions:

- [x] **Reward**: defeating another real player now earns XP - `PVP_XP_REWARD_PERCENT` (6%) of `xp_for_level()` at the DEFEATED player's own level, split proportionally by damage like an NPC kill. Not an arbitrary number - it's the actual ratio this project's own NPCs already use (Arena Fighter ~6.4%, Arena Master ~6.1%). Deliberately XP only, not gold.
- [x] **A real bug found while building this**: `attacker.has_account` looks like "is this a real player" but is actually `self.sessions.count()` in Evennia core - whether someone is connected *right now*, not whether the character is player-created at all. Using it would have silently failed to reward a real PvP kill the instant either side's connection hiccupped. Fixed to use `.account` (the persistent link), the same check `handle_player_defeat` already uses a few lines below for the same reason. Also gated on the *contributor* side, not just the defeated side - without that, an ordinary monster killing a player in normal PvE (a constant occurrence) would have incorrectly tried to award the monster XP.
- [x] **Consent/framing**: not a code-level opt-in toggle - a policy, enforced narratively. PvP requires real in-character justification (a grudge, an insult, a feud, faction/Cult business - something your character can point to), not impulse or griefing. New `help pvp` topic states this plainly, along with the consequence: violating it draws swift, discretionary punishment from the gods - framed through Jupiter, whose own help entry now notes he deals justice to the gods of Olympus themselves, not just mortals.
- [x] **Death stakes deliberately left as-is, not addressed**: losing a PvP fight still triggers the exact same `handle_player_defeat` flow as losing to any NPC (safe respawn at level ≤5, real death to the Underworld at level 6+, half XP lost). This wasn't changed because it wasn't asked to be - worth a real decision later if a lighter consequence for consensual PvP specifically is ever wanted.
- [x] **`help mailsystem`** (not `help mail`, which is already shadowed by the mail command's own auto-help - Evennia's own help resolution gives commands priority over DB topics with the same key, confirmed directly) plus a `FriendlyCmdMailCharacter` wrapper (matching the existing `FriendlyCmdMap` pattern) so `help mail` itself now shows real, character-appropriate usage instead of the contrib's original Account-oriented docstring.

## ⏱️ Combat pacing: auto-attack, in-combat regen, shorter turns — ✅ this session

Direct response to explicit "brutal feedback" that combat's core loop was almost entirely "type attack, repeat." Confirmed via code review, not just impression: zero cooldowns exist anywhere in `world/combat.py`, and MP/SP never regenerated mid-fight at all (only `rest`, out of combat, touched them) - meaning every fight's later turns collapsed into plain `attack` the moment early-fight ability spending ran out.

- [x] **`autoattack`/`auto` command** (on by default for every character): a few seconds into your turn, if you haven't acted yet, your character automatically attacks whoever you're currently fighting. Any manual command (attack, powerattack, cast, useskill, disengage, pass) always wins the race and cancels it - checked via `combat_actionsleft`, so it can never double-act. Deliberately refuses to guess a target when more than one living opponent exists.
- [x] **In-combat MP/SP regen** (`COMBAT_REGEN_PERCENT = 0.05`, i.e. 5% of max per turn) - real, sustained tactical options across a long fight instead of a one-time opening burst followed by pure `attack` spam.
- [x] **`TURN_TIMEOUT` 30 → 20 seconds**, per direct request - no real downside found, especially now that auto-attack already covers "someone's slow to act" far better than a long timeout ever did.
- [x] 15 new tests, full suite 320/320 passing (1 intentional skip). Reloaded live and re-ran a real 1v1 and the 2v2 party scenario end to end - both completed correctly, no regressions.
- [x] **Honest verification limit, same as RespawnTimer/ItemDecayManager**: the actual delayed auto-attack firing (`evennia_utils.delay`) can only truly be exercised by a real, live-connected player session - a disposable `evennia shell` process never runs the server's own reactor loop, so a scheduled delay from one never fires. Verified the scheduling call itself happens correctly (mocked and asserted the exact call) and verified `try_auto_attack`'s full decision logic directly - but the real-time "does it actually fire ~5 seconds later" behavior is inherited confidence from `delay()` being a core, widely-used Evennia primitive, not independently re-proven here.
- [x] **Average battle duration, measured + reasoned** (see chat for full writeup): real turn counts are unchanged in shape from earlier baseline data - 11 turns for a fresh 1v1, 40 total turns across 4 fighters for a 2v2 (~10/fighter). That was never really the problem; a simple 1v1 already resolved in well under a minute of real time even before these changes. The actual fix this session targets is decision *repetitiveness* within that duration, not duration itself - fight length looks reasonable for a MUD and further shortening it isn't recommended. The next real lever for tactical depth, if wanted later, is still real cooldowns on skills/spells (flagged in the original feedback, not built).

## 💡 Feature ideas for player attraction/immersion (not yet scoped, no code started)

Brainstormed on request - picked for being strong thematic fits for Rome specifically rather than generic MUD features. Roughly ordered by impact-for-effort; none of these have any implementation started.

- [ ] **Actual Colosseum "Games."** Right now the arena is a training ground, not a spectacle. See the dedicated entry higher up in this file (Ludus/rumor/auditing section) for the discussed design - a scheduled/admin-triggered themed NPC gauntlet with amplified spectator reactions and a real reward, not a full PvP bracket - and why.
- [ ] **Earned, display-able titles from achievements - a genuine dual-title system, kept deliberately separate from the existing custom `title` command.** Design discussed and settled:
  - `db.custom_title` stays exactly as it is today - free text, fully player-controlled, unrestricted (pure self-expression, e.g. "Senator of Rome").
  - New `db.earned_titles` (a list) + `db.active_earned_title` (which one is currently displayed) - populated automatically off achievement completion (a small addition to the achievement dicts: a `"title"` field, e.g. `"the Undefeated"` on the Arena Master achievement). Can only ever contain titles actually unlocked - no faking it, same "verified, not just claimed" spirit as the existing `greet`/mask-proof identity system.
  - New commands alongside the unchanged `title <text>` / `title clear`: `titles` (list what's unlocked + which is active), `titles set <name>`, `titles clear`.
  - Display split by context rather than trying to cram both in everywhere: `who`'s compact table shows one slot only (earned title takes priority if active, falls back to custom) to keep the table from getting even more cramped than it already is (see the `who` cleanup section below); `stats`/looking directly at a player shows both, labeled separately, since there's room there.
- [ ] **A living-world rumor/news system.** NPCs occasionally mentioning recent player accomplishments ("Have you heard? Marcus defeated the Arena Master!"). Cheap to build, disproportionately high payoff for making the world feel alive rather than static - plugs directly into achievement data already being tracked.
- [ ] **New, requested: a real faction-membership mechanic, based on the 7 factions already fully written on the live website (`factions.html`) but with zero in-game presence anywhere in `world/*.py` today.** Three public Orders (Imperial Legion/Light, Praetorian Order/Grey, Hellenic Resistance/Light) and four secret Cults (Mithras/Light, Orphic Mysteries/Grey, Cult of Hecate/Evil, Cult of Bacchus/Grey). This is deliberately distinct from the Collegia idea just above - static, lore-authored factions a character is initiated into, not a player-created guild. The website's own "why join" copy already sketches real mechanical hooks worth building toward: Imperial Legion → Legionary/Gladiator/Barbarian + frontier content; Praetorian Order → court intrigue + standing in the Colosseum (the site claims a "Senatorial Podium" - verify this room actually exists before promising it in-game); Hellenic Resistance → Venator/Speculator + guerrilla content, thematically tied to Apollo/Diana; Cult of Mithras → a hidden mithraeum + cross-faction recognition; Orphic Mysteries → unique dialogue and an easier path specifically at the Underworld's Threshold of Return (a real, already-built room); Cult of Hecate → synergy with Haruspex's existing Blood Sacrament (a real skill); Cult of Bacchus → synergy with Barbarian's rage. **Real open questions to settle before building**: (1) the website explicitly says joining a Cult "is meant to be a real roleplay journey, not a menu option" - a simple `faction join <name>` command for the Cults specifically would contradict that stated design intent, so Cults likely need some kind of gated/RP-initiation flow while the public Orders can probably be a plain command; (2) fix the "Praetorian Guard" (homepage) vs "Praetorian Order" (factions page) naming mismatch on the website itself first, so the in-game name doesn't inherit the ambiguity.
- [ ] **New, requested: a religion/piety mechanic for mortal characters** - the website (`gods.html`) frames the pantheon as "active presences... watching, favoring, and occasionally interfering," but today that's only true for the Cursus Divinorum god-tier ladder (a player character *becoming* a god) - there's no way for an ordinary mortal character to worship, pray to, or earn small standing with a specific deity. **Blocking issue found while scoping this, needs a decision before building**: the website's pantheon and the in-game pantheon already disagree. `gods.html` lists 12 Olympians (including Apollo) plus Pluto and Trivia as "Other Powers" - 14 total. The real in-game `PANTHEON` dict (`world/god_help.py`, already live as help entries) has 13: the same 12 minus Apollo, *plus* Vesta, and no Trivia/Hecate at all. Pick one canonical list and reconcile the other before scoping piety mechanics around specific gods. Rough shape once that's settled: a small `db.piety` standing per deity, gained through thematically-appropriate triggers that already exist (praying at one of the Capitoline Hill's real temple rooms - the Temple of Jupiter Optimus Maximus and Juno Moneta's temple at the Arx already exist - or via achievement-adjacent triggers like a Legionary's fight win nudging Mars favor), paying out as small stat bonuses, unique NPC dialogue, or a title - reusing the achievement/faction patterns rather than inventing a new system from scratch. Keep this clearly distinct from Cursus Divinorum in framing: that system is about becoming a god; this one is about a mortal's relationship with the gods that already exist.
- [ ] **Collegia - player-run guilds.** Historically authentic (collegia were real Roman trade/social guilds), and distinct from the existing static lore factions. Player-created, player-led, real ranks. Gives long-term players a reason to organize beyond a temporary party, and gives Rome-the-city a natural building type (guild halls) once it exists.
- [ ] **Bounties and quests - two distinct things, worth building as two separate systems, not one.** Raised directly after brutal feedback that the only structured activity loop right now is "grind NPCs," with no other answer to "what do I do today."
  - **Bounties**: a repeatable board, simple "kill X" / "fetch Y" objectives for gold/XP, regenerating over time. Cheap to build, immediately gives new/returning players a clearer default than open-ended grinding.
  - **Quests**: one-time, narrative-driven objectives with a real story beat and a unique (non-repeatable) reward - a title, a specific item, a lore payoff. The only thing resembling this today is the single scripted Colosseum escape sequence; everything past that point is unstructured. This is the more valuable of the two long-term (it's what actually makes content feel *written*, not generated), but real design work (writing actual quest content, deciding on a tracking/state system per quest) is needed before it's buildable - the bounty board is the quick win, quests are the real investment.
- [ ] **`top`/leaderboard command.** Top players by level, gold, or achievements. Cheap, social, quietly competitive.
- [ ] **Bump `extended_room` (time-of-day descriptions) up the existing contrib priority list.** Already chosen, currently unprioritized. Given the amount of care already put into atmosphere (the Underworld color-palette work, room descriptions throughout), this is disproportionately high-immersion for the effort.
- [ ] **Bump in-character `mail` up the existing contrib priority list too.** Also already chosen, also currently low priority. Given how much social infrastructure already exists (sdesc/mask/recog/greet), letters between characters is a natural next social layer that's currently missing.
- [ ] **Colosseum end-game content for level 100 players - brainstormed this session, nothing scoped/built yet.** Full list given in chat; top picks by impact-for-effort: (1) a real "Games" event system (see the Actual Colosseum Games idea above, but specifically framed as the level-100 answer - a champion's bracket, spectator reactions, a crowd-favor stat); (2) a genuine end-game boss (an undefeated champion/gladiator legend, meaningfully harder than the current Champions' Court roster, with unique drops); (3) a prestige/rebirth-style system once level 100 is hit, so there's a reason to keep engaging rather than the level bar just going flat; (4) cosmetic-only arena titles/regalia earned specifically from Colosseum content, tying into the earned-titles idea above.
- [ ] **New, requested: "what do I do after the Ludus" - the real mid-game content gap, named explicitly rather than left implicit.** Raised directly after brutal feedback: the Colosseum onboarding (cells → escape → Ludus tiers → Deeper Sands) is a complete, polished first-hours loop, but a player who finishes it hits a wall - Forum Romanum and Capitoline Hill are built and lore-rich but largely *passive* (NPCs to look at and talk to, not quest-driven activities), and there's no scripted content between "you're done with the Ludus" and "you're a level-100 god-tier candidate." This isn't one feature, it's the connective tissue between several already-scoped ones - the actual fix is largely already identified elsewhere in this file and just needs prioritizing together: the Colosseum Games event system, quests (see the bounties/quests entry above), factions/religion giving Forum/Capitoline NPCs a reason to matter mechanically rather than just narratively, and Collegia giving players something social to build toward. Worth treating as a named priority bucket, not scattered separate ideas, next time a content-focused session happens.

- [x] **Critical**: level 6+ death never actually moved the player to the Underworld. `handle_player_defeat` deliberately leaves HP at 0 while dead, but `CombatCharacter.at_pre_move` unconditionally blocks any move at hp≤0 - the move silently failed every time. Fixed with an explicit `force_move` bypass for that one system-authorized relocation.
- [x] **Critical, found while reviewing tonight's Underworld rebuild**: dead players (`is_dead=True`, hp=0) could not move through *any* normal exit at all - not just the initial drop-off. This made the entire new Elysium/Tartarus/Asphodel expansion unwalkable by an actual dead player; only a superuser (full HP) could ever see it, which is exactly why neither of us had noticed. Fixed: `at_pre_move` now also allows movement when `db.is_dead` is true, distinct from someone merely knocked to 0 HP mid-fight (who's still correctly blocked).
- [x] **Major**: every self-targeted spell/skill (target type `"anychar"` - `cure wounds`, `field dressing`, `antidote`, `sanctuary`, `testudo`, `rally`, `ward against death`, and 14 others) failed with "requires a target" when cast with no argument, instead of defaulting to the caster. The self-fallback code existed but was unreachable - an earlier validation check returned before it could ever run. This meant a Medicus typing `cast cure wounds` to heal themselves - probably the single most common support-caster action - never worked.
- [x] **Major**: using *any* item never actually consumed a limited use or spent the combat action. Every `itemfunc_*` returns `False` explicitly on failure but nothing (`None`) on success; `use_item`'s check treated both as failure and bailed before reaching `spend_item_use`/`spend_action`. Net effect: potions were functionally infinite, and using an item in combat cost nothing.
- [x] **Major**: the shop's "infinite stock" design was completely broken. `_buy` checked `ware.db.prototype_key` to decide whether to spawn a fresh copy - but Evennia's spawner never actually sets that as a `.db` attribute (it's tracked as a Tag instead). Every purchase silently handed over the real display item rather than a copy, meaning a shop genuinely could run dry exactly as the design was meant to prevent.
- [x] `schedule_respawn`'s `move_to(None)` call was missing `to_none=True` - a defeated `RespawningNPC` never actually left the room during its respawn wait, just sat there "defeated" until the timer fired and moved it right back to where it already was.
- [x] Party `invite`/`kick` couldn't find a target by their real name unless the searcher had already `greet`-ed them or was a Builder - the same rpsystem sdesc-search root cause already documented and fixed for `attack`/`fight` (`find_combat_target`), just never applied to party. Same fix applied.
- [x] `cast <spell> = <name>` and `skill <skill> = <name>` had the identical named-target search gap as party invite - fixed the same way. `use <item> = <name>` had it too.
- [x] `at_defeat`'s XP/gold-split loops could crash (`AttributeError`) on a stale `damage_log` entry for a since-deleted contributor - the exact gotcha #2 pattern (a deleted reference reloads as literal `None`, not an object with `pk=None`) that was already fixed once in `next_turn()`, but missed here.
